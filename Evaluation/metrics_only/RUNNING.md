# Запуск бенчмарка Design2Code

Всё гоняется **только через docker**, образ `design2code-bench`. Карта проекта и
грабли окружения — [`../docs/STRUCTURE.md`](../../docs/STRUCTURE.md), результаты —
[`../docs/RESULTS.md`](../../docs/RESULTS.md).

| файл | что |
|---|---|
| `Dockerfile`, `build.sh` | сборка образа |
| `run.sh` | поднимает контейнер и прокидывает в него аргументы |
| `run_benchmark_batched.py` | **entrypoint образа**: батчи, resume, метрики |
| `render.py`, `metrics.py` | рендер через playwright и метрики Design2Code |
| `clip_server.py` | одна копия CLIP на GPU вместо копии в каждом воркере |
| `tracking.py` | ClearML, no-op без кредов |
| `run_benchmark.py` | прежний однопроходный прогон. **В образ не копируется** и ниоткуда не вызывается; лежит как референс, на него ссылаются комментарии в живом коде |
| `compare.py`, `tools/stitch_compare.py` | визуальное сравнение генераций глазами |

## 1. Собрать образ

```bash
cd Evaluation && ./build.sh
```

Свой тег — `./build.sh design2code-bench:kozlov`.

**После любой правки `.py` образ надо пересобрать** — код внутри него скопирован,
а не примонтирован. Образы собираются на каждой машине отдельно и **могут
различаться между a100-2 и a100-3**.

## 2. Запустить

```bash
./run.sh --model Qwen/Qwen3.5-4B --n-samples 484 --batch-size 484
```

Аргументы прозрачно уходят в `run_benchmark_batched.py` (`--help` там). Управление
контейнером — через переменные окружения:

| переменная | по умолчанию | что делает |
|---|---|---|
| `IMAGE_TAG` | `design2code-bench:latest` | какой образ запускать |
| `HOST_OUTDIR` | `./bench_results` | куда на хосте класть результаты |
| `HOST_HF_CACHE` | `~/.cache/huggingface` | кэш моделей и датасетов |
| `HOST_STORAGE` | `/mnt/storage-1` | общий диск; монтируется read-only по тому же пути внутри |
| `HOST_MODEL_DIR` | — | чекпоинт вне кэша и вне общего диска; монтируется по тому же пути |
| `GPUS` | `all` | `GPUS='"device=1,2"'` — **внутренние кавычки обязательны** |
| `CONTAINER_NAME` | `design2code-bench-$(id -un)` | имя контейнера, **персональное** |
| `SHM_SIZE` | `4g` | размер `/dev/shm`; при `--num-workers` под сотню ставьте `32g` |
| `FORCE_RM` | — | `1` — снести работающий контейнер-тёзку |

⚠ **`--outdir` в `run.sh` не передавать.** Внутри контейнера он всегда
`/app/output` — единственный смонтированный путь. Скрипт проверяет это явно и
останавливается: свой `--outdir` увёл бы результаты внутрь контейнера, и после
`docker rm` от них не осталось бы ничего. Место на хосте задаётся `HOST_OUTDIR`.

⚠ **Машины общие.** Имя контейнера по умолчанию содержит имя пользователя, и
работающий контейнер-тёзка не сносится, а вызывает отказ с подсказкой. Раньше
дефолт был общий на всех, и второй запустившийся молча убивал чужой прогон.

## 3. Режим декодирования — задавать осознанно

Это не деталь, а условие сравнимости чисел.

| флаг | по умолчанию | зачем |
|---|---|---|
| `--temperature` | `0` (greedy) | до 6 августа не задавался вовсе, и бенч работал на дефолте vLLM (сэмплинг T=1.0 без seed) — **все числа, снятые раньше, с новыми несравнимы** |
| `--repetition-penalty` | `1.0` (выключен) | `1.05` лечит зацикливание и даёт базе +0.145; см. [A/B на 15k](../../docs/experiments/2026-08-07-wc2m-15k-ab.md) |
| `--max-new-tokens` | `8192` | на Design2Code мало: при 8192 обрезалось до 60% сэмплов. Ставьте `16384` |
| `--max-pixels` | `2097152` | **обязан совпадать с обучением**, иначе чекпоинт мерится вне своего распределения |
| `--materialize-dom` | выключен | нужен для моделей, пишущих React/Vue: без него метрика разбирает статический исходник и не находит текстовых блоков |
| `--prompt-file` | — | чужие модели обучены на своей формулировке промпта |

Режим пишется в `summary.json` ключом `decoding`.
В ClearML он **не логируется** — там его видно только по тегам.

## 4. Прогон упал на середине

Запустите ту же команду ещё раз. `run_benchmark_batched.py` читает
`/app/output/progress.json` и продолжает с первого необработанного батча;
уже накопленные метрики не пересчитываются, итог после рестартов точный.

Начать заново — `--no-resume` (сотрёт `progress.json`, `results.csv`, `examples/`).

Резюмировать нечего, если `HOST_OUTDIR` не был смонтирован на хост: тогда
`progress.json` жил внутри контейнера и умер вместе с ним.

## 5. Смотреть прогресс

Файлы обновляются по ходу, а не в конце:

```bash
cat bench_results/progress.json
```

## 6. Результаты

| файл | что |
|---|---|
| `summary.json` | итоговые средние, `final_score`, число оценённых и исключённых сэмплов, режим декодирования |
| `results.csv` | по `--n-examples-per-batch` строк на батч — иллюстрация, **не** источник статистики |
| `examples/batch_XXXXX/` | `pred.html`, `pred_raw.html`, `pred.png`, `ref.html`, `ref.png` тех же примеров |

⚠ **`final_score` — среднее по `n_scored`, а не по `n_samples`.** Упавшие сэмплы
исключаются из среднего, а не считаются нулём, и знаменатель у разных моделей
разный. Сравнивая прогоны, смотрите `n_scored`, а не только скор.

`final_score` — **геометрическое** среднее пяти метрик (сознательное отличие от
оригинала Design2Code); арифметическое лежит рядом как `final_score_arithmetic`.

**Числа прогона переносите в [`../docs/RESULTS.md`](../../docs/RESULTS.md).**
Прогон, оставшийся только в `summary.json` на диске, теряется — так уже было с
[A/B на 15k](../../docs/experiments/2026-08-07-wc2m-15k-ab.md).
