# SFT-трек: обучение VLM генерировать HTML по скриншоту

Дообучение Qwen-VL на задаче drafting (скриншот → HTML) — LoRA и full fine-tuning.
Формат входных данных зафиксирован в [`DATA_FORMAT_CONTRACT.md`](DATA_FORMAT_CONTRACT.md).

---

## Быстрый старт

```bash
# 1. собрать образ (один раз, ~30-40 мин: компилируется flash-attn)
docker build -t sft -f Dockerfile .

# 2. поднять контейнер
docker run --gpus all -it --rm \
  -v "$PWD":/workspace \
  -v /path/to/dataset:/data \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  -e HF_TOKEN="$HF_TOKEN" \
  --shm-size=16g \
  sft bash

# 3. внутри контейнера: проверка, что всё на месте
/opt/venv/bin/python -m scripts.smoke_test

# 4. обучение (пример: 2 карты)
CUDA_VISIBLE_DEVICES=0,1 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
/opt/venv/bin/torchrun --nproc_per_node=2 --tee 3 \
  -m train.train_sft \
  --config configs/lora_ft_qwen3_vl_4b.yaml \
  --dataset_name /data
```

Код в образ **не копируется** — он монтируется в `/workspace`, поэтому правки
подхватываются без пересборки. Пересборка нужна только при смене зависимостей.

### Если образ уже собран на этой машине

`docker images | grep sft` — и сразу к шагу 2.

### Передать образ на другую машину

```bash
docker save sft | gzip > sft.tar.gz     # ~15-20 ГБ
# на целевой машине:
gunzip -c sft.tar.gz | docker load
```

Проще собрать заново из `Dockerfile` — он самодостаточен, нужен только этот
репозиторий.

## Запуски

Везде `/opt/venv/bin/python`, а не `uv run`: проект в образ не устанавливался,
`uv run` попытается пересинхронизировать окружение.

| Что | Команда |
|---|---|
| Проверка формата и бюджета токенов (без обучения, ~1 мин) | `python -m scripts.smoke_test` |
| Оверфит на 20 примерах — loss обязан упасть в 10 раз | `python -m scripts.overfit20` |
| Обучение на N картах | `torchrun --nproc_per_node=N -m train.train_sft --config ... --dataset_name ...` |
| Перегенерировать конфиги после правки `configs/gen.py` | `python -m configs.gen` |

**`overfit20` запускать первым при любом изменении пайплайна.** Если loss не
схлопывается на двадцати примерах, дело в коде (маскирование лейблов, коллатор,
target modules), а не в данных.

## Куда падают результаты

```
sft-output/<профиль>/<run_name>/
├── run_info.yaml     эффективный конфиг + метаданные рана
├── checkpoint-N/     промежуточные (каждые 20% обучения, хранятся последние 2)
└── *.safetensors     финальные веса
```

`run_name` = `<профиль>_s<seed>_<таймстамп>`, поэтому повторный запуск того же
конфига не затирает предыдущий.

Чекпоинты сохраняются **без состояний оптимизатора** (`save_only_model: true`):
для full FT 4B это ~8 ГБ вместо ~56. Цена — упавший ран нельзя продолжить
(`--resume_from_checkpoint` не сработает), он начинается заново. Для длинных
ранов (десятки тысяч примеров, часы работы) стоит запускать с
`--save_only_model false`, тогда resume возможен, но каждый чекпоинт весит
столько же, сколько веса плюс состояния AdamW.

Частота задана **долей** от общего числа шагов, а не абсолютным числом:
`save_steps: 0.2`, `eval_steps: 0.1`. Абсолютные значения на небольших датасетах
не срабатывают вовсе — шагов там всего десятки.

`run_info.yaml` — единственный надёжный способ узнать, с какими параметрами
реально шёл ран: там лежат аргументы после всех переопределений из командной
строки, а также размеры сплитов, бюджет токенов и сколько сэмплов отбраковано.
**Правка yaml на уже запущенный ран не влияет** — конфиг читается один раз.

Каталог `sft-output/` в `.gitignore`.

## Как менять параметры

Три уровня, от постоянного к разовому:

1. **`configs/gen.py`** → `python -m configs.gen`. Так задаются значения для всех
   конфигов сразу или per-model через словарь `MODELS`. Единственный способ,
   который переживёт перегенерацию.
2. **Правка `configs/*.yaml`** — до следующего `python -m configs.gen`.
3. **Флаг в командной строке** — перекрывает yaml, живёт один запуск. Для
   экспериментов удобнее всего; проверить, что применилось, — в `run_info.yaml`.

### Что важно знать

**`N_GPUS` в `configs/gen.py`** должен совпадать с реальным числом карт.
Из него считается `gradient_accumulation_steps`, а эффективный батч это
`per_device_train_batch_size × gradient_accumulation_steps × число_карт`.
Запустив конфиг, сгенерированный под 2 карты, на 4 — молча получите вдвое
больший батч и другой эффективный learning rate.

**`max_length` вычисляется**, а не задаётся: длина кода (p99 по датасету) +
промпт + визуальные токены картинки. Последнее зависит от модели, поэтому
значение у каждой своё. Подробности — в докстрингах `configs/gen.py`.

**Логирование в трекер выключено** (`report_to: none`). Включается одним
значением (`wandb` / `tensorboard`) после установки пакета в `pyproject.toml`.

**Валидация — это только `eval_loss`**, то есть обычное предсказание токенов.
Она годится как детектор поломок и переобучения, но не как метрика качества: на
WebSight loss и token accuracy насыщаются в первые же шаги (синтетика очень
шаблонная), и по ним нельзя отличить конфиг, который лучше воспроизводит вёрстку.
Настоящая метрика — рендер сгенерированного HTML и сравнение с целевым
скриншотом, это зона eval-трека.

## Замеры производительности

Full FT Qwen3-VL-4B, 2×A100 80 ГБ, ZeRO-2, `max_length` 2368, эффективный батч 64:

| конфигурация | с/шаг | примеров/с |
|---|---|---|
| `bs=4` + gradient checkpointing | 20.1 | 3.2 |
| `bs=8` + gradient checkpointing | 19.9 | 3.2 |
| `bs=4` без checkpointing | OOM | — |

GPU utilization 99% — упор в вычисления, а не в загрузку данных: рост батча и
fused-оптимизатор скорость не меняют.

Отсюда прикидка времени: **~3.2 примера/с на двух картах**, то есть 5000
примеров это 26 минут на эпоху. На четырёх картах вдвое быстрее, LoRA ещё в
полтора-два раза быстрее full FT.

**Qwen3.5 (гибридная архитектура с Gated DeltaNet) в этом образе работает в
~7 раз медленнее** — 137 с/шаг против 20. Причина: `flash-linear-attention`
требует Triton ≥3.3, а torch 2.6 жёстко пинит Triton 3.2. Лечится только
подъёмом torch до 2.7+ (и, соответственно, CUDA-индекса и базового образа).
До тех пор для замеров и обучения берите Qwen3-VL или Qwen2.5-VL.

## Диагностика

**OOM.** Порядок отступления, эффективный батч при этом сохраняется:
уменьшить `--per_device_train_batch_size` вдвое и во столько же увеличить
`--gradient_accumulation_steps`; затем включить `--gradient_checkpointing true`.

**`nvidia-smi` не показывает реальное потребление** — там размер пула,
зарезервированного кэширующим аллокатором PyTorch, и он не уменьшается.
Сравнивать конфиги по нему бессмысленно; используйте
`--skip_memory_metrics false`, тогда в метриках появятся `*_mem_gpu_*`.

**Ран упал, карты заняты.** `torchrun` оставляет процессы-зомби:
`pkill -9 -f torchrun; pkill -9 -f train.train_sft`, затем проверить `nvidia-smi`.
PID-ы внутри контейнера и на хосте разные, имена процессов `nvidia-smi` в
контейнере обычно не показывает — смотрите на занятую память.

**Трейсбек не виден при падении на нескольких картах.** Запускать с
`--tee 3 --log-dir <путь>`: логи каждого ранга дублируются в консоль с префиксом
и складываются в файлы.

**Долгая работа по SSH** — оборачивайте в `tmux`, иначе разрыв соединения убьёт
обучение.
