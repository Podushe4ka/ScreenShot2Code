# SFT-трек: обучение VLM генерировать HTML по скриншоту

Дообучение Qwen-VL на задаче drafting (скриншот → HTML) — LoRA и full fine-tuning.
Формат входных данных зафиксирован в [`DATA_FORMAT_CONTRACT.md`](DATA_FORMAT_CONTRACT.md).
Замеры скорости и разбор узких мест — в [`THROUGHPUT.md`](THROUGHPUT.md).

---

## Быстрый старт

```bash
# 1. собрать образ (один раз, ~30-40 мин: компилируется flash-attn)
./build.sh

# 2. секреты — в .env рядом с run.sh (он под .gitignore)
cat > .env <<'EOF'
HF_TOKEN=...
CLEARML_API_ACCESS_KEY=...
CLEARML_API_SECRET_KEY=...
EOF
chmod 600 .env

# 3. проверка, что всё на месте (без GPU, ~1 мин)
DATA_DIR=/путь/к/датасетам ./run.sh python -m scripts.smoke_test

# 4. обучение на 2 картах
DATA_DIR=/путь/к/датасетам ./run.sh \
  torchrun --nproc_per_node=2 --tee 3 \
  -m train.train_sft \
  --config configs/full_ft_qwen3_5_4b.yaml \
  --dataset_name /data/имя_датасета
```

Код в образ **не копируется** — он монтируется в `/workspace`, поэтому правки
подхватываются без пересборки. Пересборка нужна только при смене зависимостей.

Долгие прогоны запускайте отвязанными от терминала, иначе разрыв SSH их убьёт:

```bash
nohup ./run.sh torchrun ... < /dev/null > run.log 2>&1 &
```

`< /dev/null` обязателен: без него `run.sh` увидит терминал, поднимет контейнер
с `-it`, и фоновое задание встанет по `SIGTTIN`.

## `run.sh`

### Что монтируется

| хост | в контейнере | переменная |
|---|---|---|
| корень репозитория | `/workspace`, cwd `/workspace/SFT` | — |
| `SFT/.container-home/` | `/container-home` — `$HOME`, кэши, `TMPDIR` | `CONTAINER_HOME` |
| `~/.cache/huggingface` | `/hf-cache` — веса моделей | `HF_CACHE` |
| `/mnt/storage-1/data` | `/data` — датасеты | `DATA_DIR` |
| не монтируется | `/out` — результаты, если задан | `OUT_DIR` |

Монтируется **корень репозитория**, а не `SFT/`: иначе ClearML не видит `.git` и
записывает слепок кода вместо коммита. Рабочий каталог при этом прежний, поэтому
относительные пути (`configs/`, `sft-output/`) не меняются.

`OUT_DIR` нужен, когда домашний раздел тесен: чекпоинты, логи экспериментов и
снапшоты уезжают на просторный диск. Скрипты сами пишут в `/out`, если он есть.

### Что задаётся в окружении

`.env` рядом с `run.sh` читается автоматически (`ENV_FILE` меняет путь). Туда
удобно сложить и секреты, и постоянные пути:

```
HF_TOKEN=...
CLEARML_API_ACCESS_KEY=...
CLEARML_API_SECRET_KEY=...
CONTAINER_HOME=/mnt/storage-1/me/container-home
HF_CACHE=/mnt/storage-1/me/hf-cache
OUT_DIR=/mnt/storage-1/me/out
```

Переопределяемое: `IMAGE`, `GPUS`, `SHM_SIZE`, `DATA_DIR`, `OUT_DIR`,
`CONTAINER_HOME`, `HF_CACHE`, `CLEARML_PROJECT`, `CLEARML_TASK`,
`CUDA_MODULE_LOADING`, `PYTORCH_CUDA_ALLOC_CONF`, `CUDA_VISIBLE_DEVICES`.

Внутрь пробрасываются ещё `RESULT_DIR`, `OUT`, `DATASET`, `CONFIG`, `NPROC`,
`ONLY`, `STEPS`, `SKIP_EXISTING`, `EXTRA_ARGS`, `RUN_ENV`, `TRACE_PATH`,
`MEM_SNAPSHOT` — ими управляются скрипты замеров, не заходя в контейнер.

### Что выставлено принудительно

| | зачем |
|---|---|
| `CUDA_MODULE_LOADING=EAGER` | **+27% скорости**: иначе драйвер догружает бинарники ядер посреди прогона (см. THROUGHPUT.md) |
| `TMPDIR=/container-home/tmp` | иначе временные файлы в `/tmp` контейнера, и при нехватке места torchrun падает с `No usable temporary directory` |
| `TRITON_CACHE_DIR`, `TORCHINDUCTOR_CACHE_DIR` | кэш компиляции переживает перезапуск контейнера |
| `PYTHONUNBUFFERED=1` | без него `print` из обучения виден только по завершении процесса |
| `PYTHONFAULTHANDLER=1` | при SIGSEGV печатается питоновский стек, а не только код возврата |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | меньше фрагментации |

### От кого работает контейнер

По умолчанию от root — запуски делает один человек, и root-овы файлы в
`sft-output/` и кэше HF ему не мешают.

`RUN_AS_USER=1 ./run.sh` запускает от uid/gid хоста. Нужно, только если к
результатам ходит кто-то ещё.

Режимы не стоит смешивать. Root оставляет в `~/.cache/huggingface` файлы и
lock-и, которые обычный uid потом не перезапишет — запуск падает на
`PermissionError` в `hub/.locks/...` либо на невнятном `Can't load tokenizer`.
Чинится из root-контейнера (`/hf-cache` — тот же каталог на хосте):

```bash
./run.sh chown -R <uid>:<gid> /hf-cache
```

Root-овы файлы в репозитории удаляются так же:

```bash
docker run --rm -v "$PWD":/w -w /w sft rm -rf <что удалить>
```

## Запуски

Везде `/opt/venv/bin/python`, а не `uv run`: проект в образ не устанавливался,
`uv run` попытается пересинхронизировать окружение. В `PATH` контейнера
`/opt/venv/bin` первым, поэтому обычно достаточно `python` и `torchrun`.

| Что | Команда |
|---|---|
| Формат, маскирование лосса, бюджет токенов (без GPU) | `python -m scripts.smoke_test` |
| Оверфит на 20 примерах — loss обязан упасть в 10 раз | `python -m scripts.overfit20` |
| Обучение на N картах | `torchrun --nproc_per_node=N -m train.train_sft --config ... --dataset_name /data/...` |
| Перегенерировать конфиги после правки `configs/gen.py` | `python -m configs.gen` |
| Архитектура модели, параметры, типы слоёв | `python -m scripts.model_facts --load-weights` |

**`overfit20` запускать первым при любом изменении пайплайна.** Если loss не
схлопывается на двадцати примерах, дело в коде (маскирование лейблов, коллатор,
target modules), а не в данных.

### Замеры скорости

| Что | Команда |
|---|---|
| Матрица конфигураций (22 эксперимента, ~2 ч) | `bash scripts/throughput_matrix.sh` |
| Один эксперимент из матрицы | `ONLY=accum8 bash scripts/throughput_matrix.sh` |
| Сводная таблица по логам | `python -m scripts.throughput_report <каталог логов>` |
| Профиль ядер и памяти | `torchrun --nproc_per_node=2 -m scripts.profile_steps ...` |
| Всё подряд без присмотра | `bash scripts/run_all.sh` |

Методика (почему нельзя верить `train_tokens_per_second` из первой строки лога,
зачем прогрев и ожидание освобождения карт) — в [THROUGHPUT.md](THROUGHPUT.md).

## Куда падают результаты

```
sft-output/<профиль>/<run_name>/
├── training_args.bin   эффективные аргументы (сохраняет сам HF)
├── checkpoint-N/       три штуки: на 33%, 66% и 99% обучения
└── *.safetensors       финальные веса
```

`run_name` = `<профиль>_s<seed>_<таймстамп>`, поэтому повторный запуск того же
конфига не затирает предыдущий. Это же имя уходит в `CLEARML_TASK`, если он не
задан явно — иначе ClearML переиспользует задачу с тем же именем и **стирает
логи предыдущего прогона**.

Если домашний раздел тесен, уводите вывод на хранилище: `--output_dir /out/...`
при заданном `OUT_DIR`. Три чекпоинта 4B это ~24 ГБ, 9B — ~54 ГБ.

Чекпоинты сохраняются **без состояний оптимизатора** (`save_only_model: true`):
для full FT 4B это ~8 ГБ вместо ~56. Цена — упавший ран нельзя продолжить
(`--resume_from_checkpoint` не сработает). Для длинных ранов стоит запускать с
`--save_only_model false`.

Частота задана **долей** от общего числа шагов, а не абсолютным числом:
`save_steps: 0.33`, `eval_steps: 0.3`. Абсолютные значения на небольших
датасетах не срабатывают вовсе — шагов там всего десятки.

**Правка yaml на уже запущенный ран не влияет** — конфиг читается один раз при
старте. Что реально применилось, показывает строка `meta:` в начале вывода:
размеры сплитов после фильтрации, бюджет токенов, доля отбракованного и
**фактический оптимизатор**.

Каталог `sft-output/` в `.gitignore`.

## Как менять параметры

Три уровня, от постоянного к разовому:

1. **`configs/gen.py`** → `python -m configs.gen`. Значения для всех конфигов
   сразу или per-model через словарь `MODELS`. Единственный способ, который
   переживёт перегенерацию.
2. **Правка `configs/*.yaml`** — до следующего `python -m configs.gen`.
3. **Флаг в командной строке** — перекрывает yaml, живёт один запуск.

### Что важно знать

**`N_GPUS` в `configs/gen.py`** должен совпадать с реальным числом карт. Из него
считается `gradient_accumulation_steps`, а эффективный батч это
`per_device_train_batch_size × gradient_accumulation_steps × число_карт`.
Запустив конфиг, сгенерированный под 2 карты, на 4 — молча получите вдвое
больший батч и другой эффективный learning rate.

**`max_length` вычисляется**, а не задаётся: бюджет под код
(`CODE_BUDGET_TOKENS`) + промпт + визуальные токены картинки. Последнее зависит
от модели, поэтому значение у каждой своё. Сейчас 16384 при 2048 визуальных
токенах. Занижение бюджета режет распределение train — `filter_by_length`
выбросит длинные примеры, и модель будет учиться на коротких.

**Одна эпоха, а не три** (`num_train_epochs: 1`). Повторные проходы по
небольшому корпусу — это заучивание: train- и eval-loss продолжают падать, а
качество на бенче деградирует. Чтобы сохранить объём обучения, нужен втрое
больший датасет, источники есть.

**`optim` при full FT игнорируется.** DeepSpeed создаёт оптимизатор сам по блоку
`"optimizer"` в своём json (получается `FusedAdam` — тоже фьюзед, потери
скорости нет). Менять оптимизатор для full FT надо в
`configs/deepspeed_zero*.json`, а не в yaml. Что применилось — видно в строке
`meta:`.

**Батчинг по бюджету токенов** (`train/batching.py`, флаг
`--max_tokens_per_batch`) реализован, но **выключен**: на текущих данных он
вдвое сокращает число микробатчей и не меняет скорость. Может пригодиться на
датасете с бо́льшим разбросом длин, а также как условие для захвата CUDA-графов —
`--length_bucket` сводит число различных форм тензоров к десятку.

**Логирование в трекер выключено** (`report_to: none`), но включается само, если
в окружении есть `CLEARML_API_ACCESS_KEY`.

**Валидация — это только `eval_loss`**. Она годится как детектор поломок, но не
как метрика качества: loss и token accuracy насыщаются в первые же шаги, и по ним
нельзя отличить конфиг, который лучше воспроизводит вёрстку. Настоящая метрика —
рендер сгенерированного HTML и сравнение с целевым скриншотом, это зона
eval-трека.

## Производительность

Актуальные числа и разбор — в [THROUGHPUT.md](THROUGHPUT.md). Коротко, full FT
Qwen3.5-4B на 2×A100, `max_length` 16384:

```
3571 токена/с   MFU 16%   ~0.48 примера/с
```

Отсюда планирование: **15 тыс. примеров — 8.7 ч на двух картах, 4.4 ч на
четырёх**. LoRA ещё в полтора-два раза быстрее full FT.

Что проверено и **не** даёт выигрыша: стадия ZeRO, размер микробатча (4 —
оптимум), длина, батчинг по токенам, размер бакетов DeepSpeed. Выключить
`gradient_checkpointing` нельзя ни при какой длине — OOM. `torch.compile` на
двух картах не влезает по памяти.

## Диагностика

**OOM.** Порядок отступления, эффективный батч сохраняется: уменьшить
`--per_device_train_batch_size` вдвое и во столько же увеличить
`--gradient_accumulation_steps`. Из 80 ГБ карты ~38 ГБ занимают веса, градиенты и
состояния AdamW — они не зависят ни от длины, ни от батча, и делятся между
картами: на четырёх картах освобождается ~15 ГБ на карту.

**`FileNotFoundError: ...kernel.ptx` или `.cubin`.** Гонка рангов за общий кэш
Triton. Лечится в коде (`isolate_compile_caches` разносит кэши по рангам), но
если всплывёт снова — удалить `.container-home/triton`.

**Ран упал, карты заняты.** `torchrun` оставляет процессы-зомби, и следующий
запуск падает по OOM не по своей вине — в тексте ошибки видно **два процесса** на
одной карте. `pkill -9 -f torchrun; pkill -9 -f train.train_sft`, затем
`nvidia-smi`. С хоста контейнеры гасятся так:

```bash
docker ps --filter ancestor=sft -q | xargs -r docker stop
```

**Ничего не печатается, хотя обучение идёт.** При `logging_steps: 1` первая
строка появляется после первого шага оптимизатора, а он на длинном контексте
занимает минуты. Прогресс-бар обновляется тоже по шагам. Проверить, что живо, —
по ваттам: `nvidia-smi --query-gpu=index,utilization.gpu,power.draw --format=csv -l 5`.

**`utilization.gpu` не показывает полезную работу** — это доля времени, когда
выполняется хоть какое-то ядро. Карта, ждущая соседа в NCCL, честно показывает
100% при 100 Вт. Смотрите на энергопотребление: 400-500 Вт — счёт, 100-150 Вт при
тех же 100% — ожидание.

**`nvidia-smi` не показывает реальное потребление памяти** — там размер пула
кэширующего аллокатора. Точные числа даёт `scripts/profile_steps.py` (пик
аллокаций, пик резерва, снапшот по стекам вызовов через `MEM_SNAPSHOT=...`).

**Трейсбек не виден при падении на нескольких картах.** Запускать с
`--tee 3 --log-dir <путь>`.

**Долгая работа по SSH** — `tmux` или `nohup ... < /dev/null &`.
