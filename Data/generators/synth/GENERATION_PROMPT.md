# Генерация страниц для SFT-датасета (reverse construction)

Ты пишешь **эталонные ответы** для обучающего набора. Схема обратная привычной: сначала
рождается идеальный код, потом из него рендерится скриншот, и уже этот скриншот станет
запросом к обучаемой модели. Поэтому качество страницы — это и есть качество разметки:
всё, что ты напишешь неряшливо, модель добросовестно выучит.

Тебе выдаётся пачка ТЗ (`briefs`). На каждое ТЗ ты создаёшь **ровно один HTML-файл**.

---

## Процедура: водопад, а не импровизация

Порядок взят из Flame (`Data/papers/Flame_2503.01619.pdf`, Приложение A.6, стр. 25–29).
Там же, на стр. 7, замерено, почему именно так: модели, обученные на структурном
водопадном синтезе, обходят модель на синтезе со случайными вариациями, потому что
случайность даёт «noise and unnatural variations that hinder learning robust coding
patterns». Не импровизируй по ходу вёрстки — сначала спроектируй.

Для каждого ТЗ мысленно (в рабочих заметках, **не в файле**) пройди четыре шага:

1. **Система.** Что это за продукт и для кого. Одно-два предложения.
2. **Требования.** 5–10 пунктов: какие функции и блоки обязаны быть на странице.
   Тон — продуктовые требования, детально и профессионально. Не пиши требований про
   доступность, кроссбраузерность, безопасность, тестирование — они не видны на скриншоте.
3. **Раскладка.** Перечисли блоки сверху вниз, их вложенность и пропорции. Здесь же реши,
   как в раскладку ложатся заказанные `features`.
4. **Реализация.** Только теперь пиши код — по спроектированной раскладке.

Если в ТЗ есть `layout_description` — это уже готовый шаг 3, следуй ему, а не выдумывай
свой. Если `task_description` пуст, всё содержание берётся из `layout_description`.

## Жёсткие требования (нарушение = страница отбраковывается автоматически)

### Единый файл, никакой сети

Один самодостаточный `.html`. Единственные внешние URL, которые разрешены, — пять
пиннутых ниже. Любой другой хост (шрифты Google, картинки, аналитика, другие CDN)
перехватчик рендера обрывает: страница отрисуется битой и уйдёт в брак.

### `impl: react_cdn`

Подключай ровно эти четыре тега, дословно:

```html
<script src="https://unpkg.com/react@18/umd/react.development.js"></script>
<script src="https://unpkg.com/react-dom@18/umd/react-dom.development.js"></script>
<script src="https://unpkg.com/@babel/standalone/babel.min.js"></script>
<script src="https://cdn.tailwindcss.com"></script>
```

Компоненты — в `<script type="text/babel">`, монтирование через
`ReactDOM.createRoot(document.getElementById('root')).render(<App />)`.
Оформление — утилитарными классами Tailwind.

Никаких других библиотек: ни роутера, ни стейт-менеджера, ни библиотек графиков,
ни иконочных пакетов. Всё рисуется руками. Хуки `useState`/`useMemo` можно —
страница снимается после отрисовки, интерактив в скриншот не попадёт, но состояние
по умолчанию должно давать содержательный экран.

### `impl: static_inline`

Один `<style>` в `<head>`, ноль JavaScript, ноль внешних запросов, ноль Tailwind.
Обычный CSS: grid, flex, псевдоэлементы, градиенты, тени, переменные.

### Картинки — только серый плейсхолдер

Там, где на макете была бы фотография или иллюстрация, ставь **дословно** этот блок:

```html
<div class="bg-gray-300 w-full h-48 rounded" style="background-color:#d1d5db;width:100%;height:12rem;border-radius:0.5rem;display:block;"></div>
```

Ни `<img>`, ни `background-image`, ни `<picture>`. Строка должна совпадать посимвольно:
её же подставляет `replace_images_with_placeholder` в конвертерах и в бенче, и рассогласование
разведёт обучение и замер.

Плейсхолдер широкий и высокий по своей природе. Если по месту нужен маленький кадр
(аватар, логотип, превью), оберни его в контейнер нужного размера с `overflow-hidden`:

```html
<div class="w-10 h-10 rounded-full overflow-hidden"><div class="bg-gray-300 w-full h-48 rounded" style="background-color:#d1d5db;width:100%;height:12rem;border-radius:0.5rem;display:block;"></div></div>
```

**Иконки плейсхолдером не делаются.** Иконки, логотипы-значки, стрелки, галочки — всегда
инлайновый `<svg>`. Классы `fa-*` запрещены: шрифты FontAwesome не вендорятся, вместо
иконок отрендерятся пустые квадраты.

### Текст настоящий

Никакого lorem ipsum, никаких «Заголовок 1» и «Пункт меню». Пиши осмысленный связный
текст по теме ТЗ: реальные названия разделов, живые формулировки кнопок, правдоподобные
числа в таблицах и метриках, настоящие имена и даты.

Это не украшательство: в метрике Design2Code text-score — пятая часть итога, и страница,
набитая заглушками, учит модель писать заглушки.

Язык — из поля `lang` ТЗ (`en`, `ru`, `de`, `zh`, `ja`). **Весь** видимый текст на этом
языке, включая подписи, единицы, форматы дат и разделители чисел по локали. Разметка,
имена классов и идентификаторы — всегда латиницей.

### Объём

Поле `tier` задаёт плотность, `dom_nodes` — целевой диапазон числа DOM-узлов,
`target_bytes` — размер файла:

| tier | узлов | байт | что это значит |
|---|---|---|---|
| S | 40–80 | 3–8 КБ | один экран, один-два блока |
| M | 150–300 | 8–20 КБ | полноценная страница с шапкой, несколькими секциями, подвалом |
| L | 400–900 | 18–34 КБ | плотный интерфейс: таблицы со строками, много карточек, боковая навигация |

### Потолок высоты: 2048 px при ширине 1280

Это самое важное ограничение после числа узлов, и его легко нарушить, не заметив.

Скриншот снимается при ширине 1280 и полной высоте страницы, а обучение ужимает картинку
до 2.1 мегапикселя. Значит: до высоты **1638 px** масштаб нативный, на **2048 px** ужатие
уже 0.89 (текст ещё читается), а на 3300 px — 0.71, и текст в таблицах превращается в кашу.
Модель не может воспроизвести то, чего не видит на входе, поэтому слишком длинная страница
не усложняет задачу, а делает её нерешаемой.

**Сложность набирается плотностью, а не длиной.** Тир L — это не бесконечная лента
одинаковых карточек, а насыщенный экран: боковая навигация плюс основная область,
две-три колонки рядом, широкая таблица, панель фильтров сбоку, компактные строки.
Смотри на реальные плотные интерфейсы — админки, биржевые терминалы, ERP: у них 800 узлов
умещаются в полтора экрана за счёт горизонтального деления и мелкого шага сетки.

Практические приёмы: `grid-template-columns` на 2–4 колонки для секций, боковая панель
вместо блока сверху, компактные `py-1.5`/`py-2` в строках таблиц вместо `py-4`,
горизонтальные полосы метрик вместо вертикального столбца карточек.

**Считается число узлов, а не байт.** Байты — грубый ориентир по масштабу: у `react_cdn`
исходник компактнее отрисованного дерева (данные разворачиваются через `.map()`), у
`static_inline` почти совпадает с ним, а на кириллице и CJK UTF-8 добавляет ещё 8–13%.
Если попал в диапазон `dom_nodes`, а по байтам слегка вышел — это нормально, ничего
не режь. Единственный жёсткий потолок — 34 КБ: выше страница не влезает в бюджет
обучения по токенам.

Тир L — то, ради чего всё затевается: таких страниц нет ни в одном синтетическом наборе.
Не сокращай его до «шапка и три карточки». Наполняй таблицы реальными строками (10–30),
списки — реальными элементами, а не тремя примерами с комментарием «и так далее».
Комментариев вида `<!-- ещё 20 строк -->` быть не должно: в датасет уедет буквально то,
что написано.

### Заказанные features

Все элементы из списка `features` обязаны присутствовать и быть видимыми на первом
рендере. Значения:

| feature | что сделать |
|---|---|
| `nested_tables` | таблица, внутри ячейки которой лежит вложенная таблица |
| `inline_svg_icons` | набор иконок инлайновым `<svg>` |
| `css_gradients` | линейный или радиальный градиент в фоне блока |
| `layered_shadows` | несколько теней разной глубины на разных слоях |
| `sticky_header` | `position: sticky` у шапки |
| `z_index_overlap` | элементы, намеренно перекрывающие друг друга |
| `multilevel_nav` | навигация с раскрытым вторым уровнем |
| `status_badges` | цветные бейджи статусов |
| `progress_bars` | полосы прогресса с разным заполнением |
| `star_ratings` | рейтинг звёздами (svg или символы) |
| `breadcrumbs` | хлебные крошки |
| `form_validation_states` | поля в состояниях: обычное, ошибка, успех, disabled |
| `zebra_table` | таблица с чередованием фона строк |
| `pagination` | блок постраничной навигации |
| `avatar_stack` | стопка перекрывающихся аватаров |
| `timeline_dots` | вертикальная или горизонтальная лента событий с точками |
| `pure_css_chart` | диаграмма на чистом CSS (столбцы через height/flex) |
| `inline_svg_chart` | диаграмма инлайновым `<svg>` (линия, area, донат) |
| `tabs_strip` | полоса вкладок, одна активна |
| `stat_tiles` | плитки с ключевыми числами |

### Чего в файле быть не должно

- markdown-ограждений ` ```html ` — файл начинается с `<!DOCTYPE html>`;
- блоков `<think>`, комментариев-рассуждений, любых объяснений;
- `lang`-несоответствий, TODO, заглушек, обрезанных списков;
- `<iframe>`, `<noscript>`, счётчиков, ссылок на внешние стили и шрифты.

## Что вернуть

Для каждого ТЗ запиши файл по пути `Data/synth_pilot/raw/<id>.html`, где `<id>` — поле
`id` из ТЗ. Больше ничего создавать не нужно.

В финальном ответе дай короткую таблицу: `id`, тир, `impl`, сколько получилось узлов
и байт по факту, и одной строкой — что за страница вышла. Если какое-то ТЗ выполнить
не удалось, скажи об этом прямо и объясни причину, а не подставляй упрощённую заглушку:
брак лучше поймать сейчас, чем найти его потом в обученной модели.
