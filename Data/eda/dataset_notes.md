# Заметки по датасетам — методика расчёта метрик

Общая методика (см. `required_data.md`): метрики 2–6 считаются на **случайной**
выборке (`shuffle(seed=SHUFFLE_SEED, buffer_size=SHUFFLE_BUFFER)` поверх streaming +
`.take(SAMPLE_SIZE)`), метрика 1 (количество примеров) — всегда точная, по всему
сплиту. Тяжёлые объекты (картинки, HTML) в память не накапливаются, в цикле
собираются только скалярные признаки.

> `shuffle` тасует порядок шардов (главный эффект: без него `.take` берёт весь
> sample из головы первого шарда — у WebCode2M это 1 шард из 2063) плюс локальный
> буфер. Раньше выборка была `.take(N)` «с головы» — детерминированная, но смещённая.

## Как считается метрика в каждом датасете

| # | Метрика | WebCode2M | WebUI |
|---|---------|-----------|-------|
| 1 | Количество примеров | сумма `num_rows` из footer'ов 2063 parquet-шардов train (захардкожена константой — пересчёт дорог) | `num_examples` из `dataset_info` через Hub API (датасет маленький — 29 409 в train, можно спрашивать точно каждый раз) |
| 2 | Количество языков | нативное поле `lang` | поля `lang` нет — датасет полностью английский (`card_data.language: en`); вместо разнообразия языков считаем разнообразие `source_name`/`framework`/`css_framework`/`component_type` |
| 3 | Средний размер кода (**в токенах**, Qwen — см. `token_len.py`) | `html_tokens` = токены `text` (HTML+CSS слиты) | `code_tokens` = токены HTML+CSS вместе (то, что генерит модель). Итог — p99 + рекомендуемый `max_length` |
| 4 | Среднее количество DOM-узлов | lxml по `text`: элементы + текстовые узлы | то же самое по `html` + сверка с готовым полем `element_count`, посчитанным авторами датасета |
| 5 | Размер скриншота | одно значение W×H на пример, разрешение свободное | 3 фиксированных viewport'а на `sample_id`: desktop 1280×720, tablet 768×1024, mobile 375×812 — усреднять по всем строкам без разреза по `viewport` некорректно |
| 6 | Среднее количество CSS правил | декларации `property: value` внутри `<style>` и `style=` атрибутов (CSS встроен в HTML) | CSS — отдельное поле; считаем и декларации (для сравнимости с WebCode2M), и отдельно блоки-правила `selector { ... }` (буквальное значение "правило") |

## Токенные результаты (метрика 3, токенайзер Qwen)

| Датасет | median | p99 | рабочий `max_length` | потери | вывод |
|---|---|---|---|---|---|
| WebSight **v0.2** — сырой `text` источника (`HuggingFaceM4/WebSight`, ~1.92M, Tailwind) | 418 | 835 | 896 | 0% | чистая синтетика, вся годна; v0.2 многословнее v0.1 (было 725/768) |
| WebCode2M | 3 844 | 10 114 | **10 176** | ~1% | реальные pruned, управляемые |
| WebUI | 3 052 | 171 851 | **8 000** @ cap 8k | ~25% | тяжёлый хвост |

⚠ **Строка WebSight выше — это СЫРОЙ источник (`text` с CDN-Tailwind), а не то, что
отдаёт конвертер.** Боевой drafting-таргет проходит `precompile_tailwind` — компилированный
Tailwind вшивается в инлайновый `<style>` (медиана ~6.3k символов, ~82% таргета). Из-за этого
реальная длина кода в **~4× больше** сырой. Измерено на пилоте `websight_drafting_pilot`
(4997 сэмплов, токенайзер `Qwen/Qwen3-VL-8B-Instruct`):

| WebSight v0.2 — **боевой таргет** (post-precompile) | median | p95 | p99 | max |
|---|---|---|---|---|
| код (`target_html`) | 2 321 | 3 236 | **3 815** | 4 927 |
| визуальные токены (оценка `qwen_image_tokens`) | 960 | 1 672 | 1 672 | 1 672 |
| **всего (код + картинка)** | 3 409 | 4 674 | **5 305** | 6 485 |

→ рабочий `max_length` для боевого WebSight-drafting = **6144** (код p99 округл. до 64 +
картинка p99; конвертер печатает это же в handoff). В окно SFT `max_length=8192` влезает
с запасом. **896 больше не использовать как бюджет доставляемого датасета** — это только
EDA сырого источника.

⚠ **Числа для WebCode2M/WebUI посчитаны без визуальных токенов** (`IMAGE_TOKEN_BUDGET=0`).
Реальный бюджет `max_length` = код + картинка: при 1280×720 у Qwen3-VL это ≈1.1–1.2k токенов
на скриншот (для скриншотов переменной высоты — кратно больше). Заложить `IMAGE_TOKEN_BUDGET`
после согласования разрешения с SFT.

**WebSight v0.2 — метрика 6 (CSS-правила) ≈ 0.** Стиль в Tailwind-утилити-классах, а не в
`<style>`, поэтому подсчёт правил/деклараций внутри `<style>` почти пуст — это ожидаемо и
корректно, метрика 6 для Tailwind-датасета неинформативна (сложность стиля живёт в классах).

## Сверка методики между ноутбуками

Одинаково во всех трёх: токенайзер `Qwen/Qwen3-VL-8B-Instruct`, `count_tokens(...,
add_special_tokens=False)`, `SAMPLE_SIZE=5000`, случайная выборка
`shuffle(seed=0, buffer_size=10_000)`, `count_dom_nodes` (элементы +
`//text()[normalize-space()]`), `_DECL_RE` — совпадают дословно.
(`count_dom_nodes` после перехода на `normalize-space()` даёт меньше: WebCode2M DOM 265→254.)

Два известных расхождения (задокументированы, код не меняем):
- **Расх. 1 — де-блоб только в webui.** webui чистит data-URI перед токенизацией
  (`html_clean + "\n" + css_clean`), а webcode2m токенизирует сырой `text`. Влияние
  минимально (WebCode2M — purified, base64 почти нет), поэтому оставляем как есть; при
  строгой сравнимости держать в голове.
- **Расх. 2 — источник CSS-деклараций.** webcode2m/websight считают декларации из инлайн
  `style=` и `<style>` (CSS вшит в HTML); webui — только из отдельного поля `css` (не
  ловит инлайн `style=`). Структурно оправдано разной раскладкой полей.

**WebUI — тяжёлый хвост из полноразмерных реальных сайтов** (p90 = 39 366). Гиганты — это
**не base64** (де-блоб убирает только их, тут вырезал 0), а **огромный инлайновый CSS
дизайн-систем**: пример `sample_id=002a826e` — 172k токенов, из них CSS 468k символов при
HTML всего 11k. Вывод: WebUI без фильтра по длине непригоден → cap 8192 (остаётся ~75%),
либо понизить приоритет в пользу WebSight (MVP) + WebCode2M (реальные, управляемые).

**Правило гигиены для реальных датасетов:** де-блоб (data-URI) + фильтр по токенам
(отсечка = будущий `max_length`). Всё — до учёта визуальных токенов (`IMAGE_TOKEN_BUDGET`).

## Особенности, которые нужно держать в голове

**WebCode2M**
- 2.5М строк train — полный проход дорог, все метрики кроме (1) считаются по случайной выборке (`shuffle(seed, buffer_size).take(SAMPLE_SIZE)` в streaming-режиме).
- HTML и CSS не разделены: CSS живёт внутри `<style>` и `style=` атрибутов.

**WebUI**
- Устроен как 3 строки на один `sample_id` — по одной на каждый viewport (desktop/tablet/mobile). HTML/CSS могут повторяться между вариантами одного сэмпла, это нарушает независимость наблюдений при усреднении.
- Существенно меньше (29 409 train) — можно проходить бОльшую долю сплита или целиком за разумное время (~5 мин на 8000 строк с картинками через streaming).
- Есть готовые категориальные поля (`framework`, `css_framework`, `component_type`, `source_name`) и bounding boxes каждого DOM-элемента — не используется в текущих метриках, но может пригодиться позже.
