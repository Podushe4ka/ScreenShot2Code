# Скоринг сложности и отбор по перцентилям

Общий модуль для WebUI и WebCode2M. Отвечает на вопрос «какие страницы брать в обучение»
так, чтобы ответ не свёлся к «которые длиннее».

## Зачем это не фильтр по длине

«Длинный таргет» и «сложная страница» коррелируют — и именно поэтому наивный отбор по
длине набирает не сложные страницы, а **раздутые**. Это ровно тот мусор, на котором модель
выучилась писать `<head>` на 25 тысяч символов вместо вёрстки (разбор bimodal-коллапса,
[`docs/ROADMAP.md`](../../../docs/ROADMAP.md)).

Разделяет их **плотность** — сколько видимых блоков приходится на токен кода. У честно
сложной страницы блоков много на единицу кода, у раздутой — мало. Порог задаётся
`--density-min` и применяется **до** перцентилей: иначе раздутые страницы сдвинут границы
полос, по которым идёт отбор.

### Калибровка `--density-min`

Порог должен срезать **патологию**, а не нижнюю половину источника. Замер (медиана
плотности: WebUI 0.0253, WebCode2M 0.0407):

| порог | снимет WebUI | снимет WebCode2M |
|---:|---:|---:|
| 0.005 | 2.5% | 0.0% |
| **0.01** | **9.2%** | **0.7%** |
| 0.015 | 19.8% | 4.2% |
| 0.02 | 35.5% | 12.8% |

Рабочее значение — **0.01**. При 0.02 порог попадает почти в медиану WebUI и режет уже
сложность, а не раздутость (проверено: 35% источника). На самом дне при 0.01 лежит ровно
то, ради чего барьер и заведён: страница с 86 видимыми блоками на **168 141** токен кода
и страница со 193 узлами при **одном** видимом блоке.

## ⚠ Чего структурная сложность НЕ умеет

Замер на отобранном WebCode2M (2 522 страницы) — доля площади, занятой контентом
(не белое поле и не серый плейсхолдер):

| набор | серое | белое | **чернила** |
|---|---:|---:|---:|
| синтетика (эталон «интересных») | 1.0% | 40.3% | **56.3%** |
| WebUI-inline | 0.2% | 39.4% | **44.9%** |
| WebCode2M-complex | 12.9% | 67.6% | **13.0%** |

И решающее: **чернила не связаны со сводной сложностью**. У топ-200 по `complexity`
медиана чернил 15.6%, у нижних-200 — 15.1%. То есть страница может быть на 500 узлов и
при этом на две трети пустой, а `complexity` этого не видит: она считает узлы, глубину и
объявления, а не то, нарисовано ли на странице хоть что-нибудь.

Отсюда `--min-ink` — **отдельный** барьер, не слагаемое composite.

И честная граница применимости: чернила отделяют пустое от залитого, но **не мусор от
хорошего дизайна**. Страницы с самыми высокими чернилами в WebCode2M — SEO-помойки с
цветной заливкой, календарные таблицы и шаблонные клоны одного сайта. Отбор «интересных»
страниц пиксельными и структурными признаками не решается в принципе: признак семантический,
и для него нужен либо VLM-судья, либо генерация, где содержание задаётся заданием.

## Два уровня, и это арифметика, а не лень

| Режим | Стоимость | Зачем |
|---|---|---|
| `static_features` | ~1 мс/страница | просеять ~200 тысяч кандидатов WebCode2M |
| `rendered_features` | ~0.3–1 с/страница | посчитать сложность по **отрендеренной** странице, как требует план |

Отрендерить 200 тысяч страниц нельзя ни на каком доступном железе, поэтому статика строит
шортлист, а рендер считает признаки уже по нему. В `features.jsonl` всегда есть
`render_ok` — отчёт обязан показывать, на чём именно посчитан отбор.

Признаки по рендеру, которых в исходнике нет в принципе: сколько узлов **реально видно**,
в сколько колонок легла страница (кластеры левых краёв блоков), какая доля блоков
перекрывается.

## Отбор

```bash
python score.py --staging /path/stage_webui --out feats_webui.jsonl --mode rendered -j 4
```

```bash
python select_by_complexity.py feats_webui.jsonl --out sel_webui.jsonl -n 5000 \
    --min-pct 40 --max-pct 99 --mix "0.15:40-60, 0.35:60-85, 0.50:85-99" \
    --max-total-tokens 16224 --density-min 0.01
```

Бюджет окна задаётся `--max-total-tokens` — по СУММЕ «код + картинка», а не плоским
потолком на код: визуальная часть зависит от реального размера скриншота (страница на
один экран ~900 токенов, высокая упирается в потолок ~2048). Текущее окно **16384**,
отсюда 16224 = окно минус ~160 на накладные шаблона.

Решение по умолчанию — **не «только сложные»**: снизу отрезаются тривиальные страницы
(на сниппете в десять узлов учиться нечему), сверху — монстры (за p99 начинается
раздутость, а не сложность), а внутри масса смещается в тяжёлый конец с сохранением
градиента. Набор только из сложного учится хуже смешанного и расходится с распределением
Design2Code, на котором нас меряют.

Ветка A/B «весь набор из p85+» — флаг `--hard-only`.

## Сводная сложность

`complexity` = взвешенное среднее **перцентильных рангов** признаков внутри набора
(`features.composite_scores`). Ранги, а не сырые числа: узлы измеряются сотнями, колонки —
единицами, складывать их напрямую бессмысленно. Веса — в `features.FEATURE_WEIGHTS`,
структура страницы весит больше, чем богатство отдельных элементов.

Следствие: `complexity` сравним **только внутри одного прогона** `score.py`. Это то, что
нужно отбору по перцентилям, но это не абсолютная шкала — два разных корпуса нельзя
сравнивать по этому числу.

## ⚠ Имя `select_by_complexity.py`, а не `select.py`

Каталог попадает в `sys.path` (`score.py` кладёт его туда), и файл `select.py` перекрыл бы
стандартный модуль `select` — на macOS это роняет импорт `socket`, а значит и
`ProcessPoolExecutor`, в дочерних процессах.

## Калибровка порогов — расхождение с планом

План задавал ориентир по WebCode2M: узлов p50 235 / p90 375 / p99 615, доля страниц
`>=400` узлов — 7.9%.

Замер на `xcodemind/webcode2m_purified` (2 777 страниц, по одной row-group из каждого из
30 локальных шардов) даёт **другое**: p50 177 / p90 281 / p99 414, доля `>=400` узлов —
**1.22%**, а не 7.9%.

Медианы по отдельным шардам ровные (160–213), так что это не перекос выборки. Порог,
который на этом корпусе даёт заявленный планом выход ~8%, — **300 узлов** (7.20%), и
именно он стоит по умолчанию в [`../webcode2m/scan_complex.py`](../webcode2m/scan_complex.py).
То есть *выход* из плана воспроизводится, а *абсолютный порог* — нет.

Практическое следствие: оценка «кандидатов ~200k» завышена примерно вшестеро, если считать
её по порогу 400 узлов.
