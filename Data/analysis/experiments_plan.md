# План экспериментов и сетапов (SFT → прирост на бенчах)

Рабочий документ фазы **1–8 августа**: пачка экспериментов, цель — найти рецепт
дообучения, дающий **прирост на бенчах** над базой. Опирается на
[`datasets_overview.md`](datasets_overview.md) (§6 — уже прогнанные бенчи) и на
разбор конфаундеров бенча (см. `Evaluation/`, ветка `bench/eval-run`).

## 0. Центральный вопрос и проблема

**Вопрос:** какой сетап SFT (данные × пиксель-бюджет × модель × LoRA/full × длина)
даёт `final_score` на Design2Code **выше базы**, а не ниже при падающем train-loss?

**Симптом сейчас:** loss падает, а метрики на бенче не растут / падают. Базовые
числа (§6 обзора, `visual_eval_v3`), которые надо **побить**:

| Бенч | База | final |
|---|---|---|
| Design2Code | Qwen-3.5-9B | **0.852** |
| Design2Code | Qwen-2.5-7B | 0.816 |
| Design2Code | Qwen-3.5-4B | 0.787 |

### Что уже прогнано (обновляется)

- **1-й Tier A ран** (31 июля): Qwen3-VL-4B LoRA, WebCode2M (~5.4k сэмплов), 2.10 Мп,
  3 эпохи, **2 ч 36 мин** (4×A100). loss 0.52→0.41, eval_loss 0.395, token_acc→0.89.
- **Визуальное сравнение base↔ckpt — всё ещё смазано.** Найдено: `/mnt/storage-1/compare.py`
  (отдельный скрипт, НЕ бенч) **не передаёт min/max_pixels** → чекпоинт сравнивается вне
  трейн-распределения. То есть H1-конфаундер живёт даже после фикса бенча — фикс его не затронул.
- **Первой чистой цифры `base vs ckpt` пока НЕТ.** Сначала — фикс `compare.py` (одна строка) +
  пересъёмка, либо фикс-бенч на valset. Фаза 0 обязательна.

## 1. Гипотезы расхождения (loss↓, метрики не растут)

Ранжированы по вероятности (из разбора кода бенча):

- **H1 — рассинхрон разрешения train↔eval (главный конфаундер).** Бенч не передавал
  `min/max_pixels` в vLLM → база бенчилась на родном (большом) разрешении, а чекпоинт
  обучен на зажатом. Сравнение смазано. *Починено в `bench/eval-run` (mm_processor_kwargs).*
- **H2 — обрезка генерации по токенам.** `max_new_tokens` мал → длинный HTML
  обрывается (`finish_reason=length`) → метрики занижены. *Диагностика добавлена
  (`n_length_truncated`).*
- **H3 — читаемость входа (пиксель-бюджет).** При 1.31 Мп высокие страницы ужимались
  до <10px текста. *Поднято до Tier A 2.10 Мп.*
- **H4 — распределение train≠eval.** WebSight (синтетика) не переносится на
  Design2Code (реальные). WebCode2M ближе к бенчу по домену.
- **H5 — переобучение / деградация общих способностей** (LoRA vs full, LR, эпохи).

## 2. Фаза 0 — сначала починить ИЗМЕРЕНИЕ (без этого sweep бессмысленен)

Контроль-эксперименты, 1–2 августа. Все — на **valset** (быстро), затем Design2Code.

| E0 | Что | Как проверяем H |
|---|---|---|
| **E0.1** | Пересобрать бенч базы с `--min-pixels/--max-pixels` = train-бюджет | H1: изменится ли база при in-distribution разрешении |
| **E0.2** | Свип `--max-new-tokens` ∈ {4096, 8192, 16384} на одной модели | H2: доля `finish_reason=length` и рост final при большем лимите |
| **E0.3** | base vs ckpt на **одинаковом** `max_pixels` | H1: честная дельта дообучения |
| **E0.4** | Прогон на valset WebCode2M (не только Design2Code) | быстрый цикл + разбивка `status`/`finish_reason` |

**Гейт:** пока E0 не сойдётся (метрики стабильны, обрезки ~0, дельта base↔ckpt
объяснима) — фазу 2 не начинать.

## 6a. Пилот на 1000 примерах WebCode2M (очередь на ночь)

Запуск: `SFT/scripts/run_experiments.sh` — обучение → merge_lora → бенч
Design2Code для каждого, всё в ClearML с тегами `E<N>`, S-ID и `pilot1k`.
Задачи обучения и бенча связаны (тег `train:<id>` / `bench:<id>`).

Модель — **Qwen3.5-4B, max_length 16384**. Внимание: боевой
`lora_ft_qwen3_vl_4b_webcode2m.yaml` — это другая модель (Qwen3-VL-4B, окно
8192), для 16к он не годится.

| ID | Сетап (ось) | Обучение | +бенч | Итого |
|---|---|---|---|---|
| E1 | LoRA r16, lr 1e-4, 2.10 Мп — **референс** | 1.65 ч | 0.50 ч | 2.15 ч |
| E2 | full-FT, lr 1e-5 (ось C: ёмкость) | 1.98 ч | 0.33 ч | 2.31 ч |
| E3 | LoRA r16, **lr 3e-4** (ось F) | 1.65 ч | 0.50 ч | 2.15 ч |
| E4 | LoRA r16, **3.93 Мп** (ось A, см. ниже) | 1.99 ч | 0.50 ч | 2.49 ч |
| E5 | LoRA **r64** (ось C: промежуточная ёмкость) | 1.65 ч | 0.50 ч | 2.15 ч |
| | **вся очередь последовательно** | **8.9 ч** | **2.3 ч** | **≈11.3 ч** |

Расчёт: 7.4к ток/пример (замер на `webcode2m_1000_split`), 3571 ток/с у full FT
с `EAGER`, бенч Design2Code 484 — 18–22 мин по факту (`Evaluation/results/*/time_results.txt`).
**Скорость LoRA (~4400 ток/с) — оценка, не замер:** в THROUGHPUT ось LoRA
осталась непроверенной, так что тайминги E1/E3/E4/E5 могут поехать.

### Почему эфф. батч 16, а не 64

На 1000 примерах при эфф. батче 64 выходит **46 шагов оптимизатора на 3 эпохи** —
для сходимости мало, различия между сетапами утонут в шуме. При 16 — 187 шагов.
Микробатч 4, а не 8: по замерам `bs4` даёт 2655 ток/с против 1370 у `bs8`
(в `lora_ft_qwen3_5_4b.yaml` сейчас стоит `bs8` — вероятно, медленная форма).

### Ось A: пиксель-бюджет режет не там, где думали

Смарт-ресайз работает (min/max_pixels уходят в `AutoProcessor`), но бюджет
2.10 Мп для страницы шириной 1280 держит натуральный масштаб только до высоты
**~1638 px**. Дальше ужимается всё, включая ширину:

| исходник | что видит модель | масштаб |
|---|---|---|
| 1280×1638 | 1280×1632 | 1.00 |
| 1280×2048 | 1152×1824 | 0.90 |
| **1280×3072** | **928×2240** | **0.72** (текст мельче в 1.38×) |
| 1280×4096 | 800×2592 | 0.62 |

То есть надежда «смарт-ресайз возьмёт 3072 по высоте» **не оправдана**: ширина
падает с 1280 до 928. Для натурального 1280×3072 нужен бюджет **3.93 Мп**
(3840 визуальных токенов вместо 2048). При 16к контекста это влезает: пример
станет ~9.2к токенов вместо 7.4к. Это и проверяет **E4** — прямая проверка H3,
которую считали закрытой переходом на Tier A.

### Что смотреть утром

В ClearML фильтр по тегу `pilot1k`, сравнение по `final_score` (single values).
База, которую надо побить, — **Qwen-3.5-4B = 0.787** на Design2Code.
Полезное рядом: `n_length_truncated` (если >0 — упирается в `max_new_tokens`,
метрики занижены) и `eval_loss` против `final_score` — расхождение этих двух и
есть центральная проблема плана.

**Оговорка про 1к:** это пилот на порядок меньше боевого корпуса. Он даёт
относительный порядок сетапов и проверяет, что пайплайн сквозной, но абсолютные
числа с 1000 примеров на 50k не переносятся, и часть различий может не выйти за
шум. Полноценный вывод — на оси H (размер обучения).

## 7. Трек дистилляции UI2Code^N (параллельно свипам)

Отдельная ветка: не дообучать на «сырых» реальных данных, а **дистиллировать сильного
учителя** UI2Code^N (arXiv:2511.08195, PDF в `Data/papers/`). Гипотеза — качественные
teacher-таргеты чище шумного WebCode2M и ближе к тому, что мерит бенч.

**Подготовка (закрыть до старта трека):**
- [ ] Достать учителя: веса на HF / чекпоинт / API? Проверить лицензию на использование выходов.
- [ ] Уточнить формат вывода UI2Code^N (Tailwind? inline-style? целая страница или компонент?) —
  привести к нашему drafting-контракту (`SFT/DATA_FORMAT_CONTRACT.md`).

**Пайплайн (hard-label дистилляция — проще, начать с неё):**
1. Прогнать учителя по нашим скринам (WebCode2M / собственный краул) → пары `(скрин, HTML_teacher)`.
2. Прогнать через тот же конвертер (плейсхолдеры, precompile) — как обычный drafting-датасет.
3. SFT студента (Qwen3-VL-4B) на teacher-таргетах, тот же сетап что S0.
4. Сравнить на Design2Code: **студент-на-teacher** vs S0 (студент-на-WebCode2M) vs base.

**Позже (если hard-label даёт прирост):** soft-label / логит-дистилляция — дороже, но переносит
и «как думает» учитель, а не только финальный HTML.

**Открытые:** доступность и лицензия UI2Code^N; сколько teacher-пар генерить (стоимость инференса
учителя); фильтровать ли teacher-выходы по рендеру (выкидывать не-рендерящиеся).

## 8. Протокол метрик и гигиена

- **Метрика:** `visual_eval_v3` → `final_score` (+ block/text/position/color/clip),
  `Evaluation/metrics.py`. Основной бенч — **Design2Code (484)**.
- **Порядок:** сначала valset (быстро, разбивка `finish_reason`/`status`), только
  прошедшие — на Design2Code.
- **Бенч запускать с train-бюджетом пикселей** (`--max-pixels` = как в конфиге модели).
  Для чекпоинта на старом 1.31 Мп → `--max-pixels 1310720`.
- **Фиксировать в таблицу:** ID сетапа, base-дельта, `n_length_truncated`,
  `train_runtime`, `run_info.yaml` пути. Один сетап = одна строка.
- **Декотаминация:** бенчи НИКОГДА в train (Design2Code, Web2Code-eval — держать
  train↔eval раздельно).
